## 2. 项目一：Audio-Sentry（智能听觉感知服务）

**代号**：`Audio-Sentry`  
**定位**：系统的"耳朵" - 负责听、记、存  
**目标**：构建一个**只进不出**的数据生产者，实时接收音频流，并行执行声纹识别（SV）和语音转写（ASR），利用V3.3对话智能引擎进行对齐，最终将结构化的"谁在什么时候说了什么"写入IoTDB时序数据库。  
**当前状态**：✅ 核心功能已完成，🚀 **准备封装为独立项目**。

**重要更新**：
- V2.0引擎已完全移除，由V3.0对话智能引擎取代
- 滑动窗口技术已移除，V3.0使用并行感知架构
- 系统现在使用V3.0并行感知模式作为唯一识别引擎
- IoTDB连接器已集成，数据持久化功能已完成
- 阶段3、4代码（LLM融合）已清理，项目一已满足封装条件

    2.  **技术选型与原因**：
        *   **语音活动检测 (VAD) - Silero VAD**
            *   **选择原因**：在众多VAD模型中，Silero VAD以其**极高的准确率**和**极低的计算资源消耗**而著称。它能在CPU上实时运行，并且对各种背景噪音（如餐厅嘈杂声、音乐声）有很强的抵抗力，能精准地"掐头去尾"，只提取有效的人声片段，这是保证后续识别精度的关键第一步。
        *   **声纹识别模型 - ERes2NetV2**
            *   **选择原因**：这是由阿里巴巴达摩院研发的、在业界权威声纹识别挑战赛（VoxCeleb）中名列前茅的模型。它通过独特的残差网络结构（Res2Net）和多尺度特征提取能力，能够捕捉到声音中极其细微的、能够区分不同人的特征。选择它，就是选择了**业界顶级的识别精度**作为我们系统的技术内核。
*   **产出**：详细的《系统架构设计文档》与《数据库设计文档》，为后续开发提供了清晰的蓝图。

### 2.3 开发与实现 (✅ 已完成)

*此阶段的目标是"动手把系统造出来"，将设计图纸转化为可运行的代码。*

*   **工作内容**（依据架构图层次）：

    **2.3.1 声纹注册模块实现**：
    1.  **音频预处理与验证层**：
        *   音频格式验证（采样率、声道、数据类型检查）
        *   RMS能量检查（过滤静音和远端噪声）
    2.  **VAD切分与质量检测层**：
        *   VAD切分（Silero VAD检测语音片段）
        *   片段时长过滤（过滤<0.5秒的片段）
        *   SNR质量检测（过滤SNR<5dB的片段）
    3.  **声纹特征提取层**：
        *   原始特征提取（ERes2NetV2提取192维特征）
        *   加噪增强（可选，与背景噪音混合）
        *   特征平均（原始+加噪特征平均）
    4.  **阶梯式质量控制层**：
        *   质量准入门槛（检查片段数量和总时长，<3片段或<5秒则注册失败）
        *   片段选择策略（标准态：3-10片段全部使用；理想态：>10片段随机采样8个）
    5.  **加权平均计算层**：
        *   计算几何中心（初步质心）
        *   计算余弦距离（各向量到中心的距离）
        *   高斯函数加权（距离越近权重越高）
        *   加权平均（计算最终质心）
        *   L2归一化（归一化特征向量）
    6.  **向量存储层**：
        *   存储后端选择（Redis/本地文件）
        *   用户存在检查（避免意外覆盖）
        *   特征向量存储（保存embedding和元数据）

    **2.3.2 V3.0对话智能模式实现**：
    1.  **音频预处理层**：
        *   采样率检查与重采样（统一到16kHz）
        *   声道转换（多声道→单声道）
        *   格式验证（数据类型、数值范围）
    2.  **RMS能量门限过滤层**：
        *   RMS能量计算（计算均方根值并转换为dB）
        *   阈值判断（过滤低能量音频，< -25dB视为静音/远端噪声）
    3.  **阶段1：并行感知层**：
        *   **声纹识别分支（SV Branch）**：
            *   细粒度VAD切分（200ms最小静音时长）
            *   声纹特征提取（FBank特征→ERes2NetV2深度网络→192维embedding）
            *   向量存储与比对（1:N向量检索，Redis/本地文件存储）
            *   AS-Norm评分（Cohort数据集归一化，Z-score计算，阈值过滤）
        *   **ASR识别分支（ASR Branch）**：
            *   词级别转录（Faster-Whisper Large-v3，词级别时间戳，中文识别）
            *   时间戳提取（词列表，时间戳+置信度）
        *   **结果合并**：合并SV和ASR两个分支的结果
    4.  **阶段2：对话智能引擎（DiarizationEngine）**：
        *   词-说话人对齐（Word-Speaker Alignment）：对每个ASR词找到时间上重叠最多的SV片段，计算重叠时长和重叠率，置信度检查
        *   边界校正（Boundary Correction，V3.3）：识别说话人切换边界，基于SV片段结束时间定义嫌疑区，对嫌疑区内的词重新评估，修正边界附近的归属错误
        *   置信度感知的聚合（Confidence-Aware Aggregation）：锚点修正，合并连续的同说话人词语，计算平均Z-score
    5.  **结果输出层**：
        *   结果汇总逻辑（主要说话人判定、说话人统计）
        *   绝对时间戳添加（UTC时间戳转换）
        *   详细日志记录（写入日志文件）
    6.  **IoTDB连接与写入层**：
        *   连接建立（IoTDB Session连接）
        *   批量写入对话流（insert_dialogue_transcript）
*   **产出**：一套功能完整、性能卓越、稳定性高的多模态对话智能分析系统（版本 V3.3），包含声纹注册模块和V3.0对话智能模式。

## 3. 项目二：Brain-Core（通用大模型推理服务）

**代号**：`Brain-Core`  
**定位**：系统的"大脑" - 纯粹的计算单元  
**目标**：构建一个**无状态**的API服务，不包含任何业务逻辑，只负责将Qwen2.5大模型加载到显存中，并以极高的吞吐量响应外部的推理请求。兼容OpenAI API格式，方便任何客户端调用。

## 4. 项目三：Logic-Flow（多模态业务编排系统）

**代号**：`Logic-Flow`  
**定位**：系统的"手" - 协调数据与决策  
**目标**：构建一个**轻量级**的业务逻辑中心，不跑任何重型模型，只负责"搬运"和"指挥"。从IoTDB拉取项目一（听觉）和P4服务器（视觉）的数据，拼装成Prompt，发给项目二（大脑）进行分析，最后处理结果。  
**当前状态**：✅ 需求分析与系统设计已完成，⏳ **待开发**。

### 4.1 需求分析 (✅ 已完成)
*   **工作内容**：定义了"有效推销"、"服务怠慢"等多个需要融合分析的典型业务场景，明确了系统需具备时序对齐、Prompt工程、推理调用、结果处理的核心能力。
*   **产出**：《Logic-Flow需求规格说明书》。

### 4.2 系统设计 (✅ 已完成)

*此阶段的目标是明确"我们该怎么做"，设计系统的技术架构、数据结构和接口规范。*

*   **工作内容**：
    1.  **架构设计**：设计了基于IoTDB时序数据库的"数据总线"架构。核心思想是"**先对齐，再分析**"。所有模态的数据（视觉、听觉）都携带精确的时间戳写入IoTDB。融合分析时，系统只需根据一个模态的时间戳，去数据库中查询同一时间窗口内的其他模态数据即可。
    2.  **技术选型与原因**：
        *   **时序数据库 - IoTDB**
            *   **选择原因**：IoTDB是专为时序数据设计的数据库，能够高效存储和查询带时间戳的多模态数据。通过精确的时间戳实现多模态数据的时空对齐，极大地降低了系统耦合度。
        *   **编程语言 - Python**
            *   **选择原因**：Python生态丰富，易于开发，且不依赖GPU资源，可以在CPU上高效运行。
    3.  **硬件方案设计**：完成了对员工佩戴式终端的硬件选型，最终确定 **Radxa Zero 3W** 方案。
        *   **选择原因**：相较于树莓派Zero 2W，Radxa Zero 3W **原生板载5GHz WiFi**，无需外接USB网卡，使得终端体积更小、功耗更低、集成更简单。在餐饮店这种2.4GHz信号干扰严重的复杂环境下，5GHz的稳定连接是保障数据实时回传的生命线。
*   **产出**：详细的《Logic-Flow系统架构设计文档》与《边缘终端硬件方案书》。

### 4.3 开发与实现 (⏳ 待启动)

*此阶段的目标是"动手把系统造出来"，将设计图纸转化为可运行的代码。*

*   **工作内容**：
    1.  **时序对齐查询器**：
        *   **功能**：从IoTDB中查询同一时间窗口内的`root.store.audio`和`root.store.visual`数据。
        *   **作用**：实现多模态数据的时空对齐，为后续融合分析提供输入。
    2.  **动态Prompt构建器**：
        *   **功能**：将多模态数据填入预设的Prompt模板（如："判断员工是否在推销"）。
        *   **作用**：将结构化的多模态数据转换为LLM可理解的文本格式。
    3.  **推理调用模块**：
        *   **功能**：通过HTTP请求调用项目二（Brain-Core）的API接口。
        *   **作用**：将构建好的Prompt发送给LLM服务，获取分析结果。
    4.  **结果处理模块**：
        *   **功能**：解析LLM返回的JSON，触发报警或存回IoTDB的`root.store.analysis`。
        *   **作用**：将LLM的分析结果转换为业务决策，完成整个融合分析流程。
*   **产出**（预期）：一套功能完整的业务编排系统，能够实现从多模态数据查询到业务决策输出的全链路流程。

### 4.4 测试与验证 (⏳ 待启动)
*   **工作规划**：建立包含"视觉+听觉"的标注数据集，评估LLM在真实场景下的判断准确率，并对端到端延迟进行压力测试。

### 4.5 部署与交付 (⏳ 待启动)
*   **工作规划**：将业务编排系统打包为独立服务，配置为常驻后台运行，实现与项目一、项目二的协同工作。

### 4.6 维护与迭代 (⏳ 待启动)
*   **工作规划**：系统上线后，建立针对多模态系统的长期监控，并探索使用线上数据对LLM进行持续微调的可能性，以提升其在特定业务场景下的分析精度。

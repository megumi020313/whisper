## 🛠️ 第一部分：硬件终端构建 (The Edge)

本部分指导如何从零组装一台具备 5G 通信、UPS 续航和麦克风阵列的智能采集终端。

### 1.1 硬件清单与组装
**所需工具**：小号十字螺丝刀、(可选)电烙铁。

1.  **焊接排针 (Pin Soldering)**
    *   **检查**：树莓派 Zero 2 W 主板是否已焊好 GPIO 排针。
    *   **操作**：如未焊接，请务必将 40Pin 排针焊接到主板上（建议找专业维修店代工，确保稳固）。

2.  **安装麦克风扩展板 (ReSpeaker HAT)**
    *   **操作**：将 ReSpeaker 2-Mics Pi HAT 对准树莓派排针，**垂直、轻柔**地按压到底。
    *   **检查**：确保无缝隙，针脚完全插入。

3.  **安装 UPS 电源模块**
    *   **操作**：使用铜柱和螺丝将 UPS 板固定在树莓派背面。确保弹簧探针（Pogo Pin）准确顶在树莓派背面的电源触点上。
    *   **连接电池**：将锂电池插头插入 UPS 板接口（注意防呆设计）。

4.  **外设连接**
    *   **SD卡**：插入烧录好系统的 TF 卡。
    *   **5G网卡**：使用 MicroUSB OTG 转接头，连接 5G USB 网卡到树莓派的 **USB 数据口**（非 PWR 供电口）。

5.  **封装外壳**
    *   将组装好的“三明治”结构装入 3D 打印外壳，锁紧螺丝。

### 1.2 系统烧录与驱动配置

1.  **烧录操作系统**
    *   使用 **Raspberry Pi Imager**。
    *   选择系统：**Raspberry Pi OS (Legacy, 64-bit) Lite** (无桌面版，最省资源)。
    *   **预配置**：开启 SSH，设置主机名 (`audio-node-01`)，配置初始 WiFi。

2.  **安装麦克风驱动 (ReSpeaker)**
    ```bash
    sudo apt-get update
    sudo apt-get install git
    git clone https://github.com/respeaker/seeed-voicecard.git
    cd seeed-voicecard
    sudo ./install.sh
    sudo reboot
    # 验证：执行 arecord -l 应看到 seeed-2mic-voicecard
    ```

3.  **安装 5G 网卡驱动 (RTL8821CU/AU)**
    ```bash
    sudo apt-get install raspberrypi-kernel-headers dkms
    git clone https://github.com/morrownr/8821au-20210708.git
    cd 8821au-20210708
    sudo ./install-driver.sh

    ```

## 🧠 第二部分：边缘端软件逻辑 (Edge Software)

**核心升级**：不再单纯录音，而是引入 **VAD（人声检测）**、**本地队列** 和 **远程控制**。

### 2.1 软件架构设计
在树莓派上运行一个 Python 守护进程 `smart_recorder.py`，包含三个核心线程：

1.  **采集线程 (Recorder Thread)**：
    *   读取麦克风流。
    *   运行 **WebRTC VAD**：仅当检测到人声时才写入缓存。
    *   **降噪**：调用 `RNNoise` 库进行预处理（可选）。
    *   生成文件：`{device_id}_{timestamp}.wav`。

2.  **通信线程 (Comm Thread)**：
    *   **心跳包**：每 60秒 向云端发送状态（电量、磁盘空间）。
    *   **指令接收**：通过 gRPC 双向流或 MQTT 接收 `START/STOP` 指令。

3.  **上传线程 (Uploader Thread)**：
    *   监控本地 `pending/` 目录。
    *   **断网重传**：有网则上传并移动到 `uploaded/`；无网则堆积在本地。
    *   **存储管理**：当 SD 卡剩余空间 < 1GB，自动删除最旧文件。

### 2.2 远程控制实现方案

**方案 A：物理开关（硬控制）**
*   **连接**：GPIO 17 接按钮，GPIO 27 接 LED。
*   **逻辑**：按下按钮 -> 触发中断 -> 切换 `is_recording` 标志位 -> LED 亮/灭。

**方案 B：云端指令（软控制）**
*   **协议**：gRPC 双向流 (Bi-directional Streaming)。
*   **逻辑**：
    ```python
    # 伪代码
    for command in stub.StreamAudio(audio_generator()):
        if command.type == "STOP_RECORDING":
            stop_capture()
        elif command.type == "REBOOT":
            os.system("reboot")
    ```

## 📡 补充章节：数据传输与上传策略 (Data Transmission Strategy)

**核心目标**：在网络不稳定、带宽有限、并发量大的工业环境下，确保音频数据**不丢失、不重复、不拥堵**。

### 1. 上传协议设计 (Interface Design)

我们放弃复杂的流式协议（如 RTSP），采用最成熟、容错率最高的 **HTTP POST (Multipart)** 方式。无论是实时切片还是定时打包，底层都复用这一套接口。

**云端接口定义 (Service A)**：
*   **URL**: `POST /api/v1/upload_audio`
*   **Header**: `Authorization: Bearer <device_token>`
*   **Body (Form-Data)**:
    *   `file`: 音频文件二进制流 (`.wav` / `.opus`)
    *   `metadata`: JSON 字符串，包含 `{ "device_id": "dev01", "timestamp": 1703568000123, "duration": 10.5 }`
    *   `checksum`: 文件 MD5 值（用于校验完整性）

---

### 2. 边缘端上传逻辑 (Edge Implementation)

在树莓派的 `smart_recorder.py` 中，**上传线程 (Uploader Thread)** 必须实现**“本地持久化队列 + 断点续传”**机制。

#### 逻辑流程图：
```mermaid
graph TD
    A[录音线程生成文件] --> B{网络通畅?}
    B -- 是 --> C[尝试直接上传]
    B -- 否 --> D[存入本地待传目录 pending/]
    C -- 上传失败 --> D
    C -- 上传成功 --> E[移入已完成目录 uploaded/ 或删除]
    
    F[后台补传线程] --> G[扫描 pending/ 目录]
    G --> H{有积压文件?}
    H -- 是 --> I[按时间顺序上传]
    I -- 成功 --> E
    I -- 失败 --> J[指数退避等待 (Retry Backoff)]
```

#### 关键代码逻辑 (Python 伪代码)：

```python
import requests
import os
import time
import hashlib

UPLOAD_URL = "http://your-v100-ip:8000/api/v1/upload_audio"
PENDING_DIR = "./data/pending"

def calculate_md5(file_path):
    # 计算文件指纹，防止传输损坏
    with open(file_path, "rb") as f:
        return hashlib.md5(f.read()).hexdigest()

def upload_worker():
    while True:
        # 1. 获取待传文件（按文件名时间戳排序，优先传旧数据）
        files = sorted(os.listdir(PENDING_DIR))
        if not files:
            time.sleep(1)
            continue

        current_file = files[0]
        file_path = os.path.join(PENDING_DIR, current_file)
        
        try:
            # 2. 构造请求
            with open(file_path, "rb") as f:
                files = {'file': f}
                data = {
                    'metadata': '{"device_id": "dev01", ...}', # 解析文件名获取
                    'checksum': calculate_md5(file_path)
                }
                
                # 3. 发送请求 (设置超时)
                response = requests.post(UPLOAD_URL, files=files, data=data, timeout=10)
                
            # 4. 处理响应
            if response.status_code == 200:
                print(f"✅ 上传成功: {current_file}")
                os.remove(file_path) # 或移动到备份目录
            else:
                print(f"❌ 服务器报错: {response.status_code}")
                time.sleep(5) # 稍后重试

        except requests.exceptions.ConnectionError:
            print("⚠️ 网络断开，进入休眠...")
            time.sleep(10) # 断网保护
        except Exception as e:
            print(f"❌ 未知错误: {e}")
            # 将错误文件移动到 error/ 目录，防止阻塞队列
            shutil.move(file_path, "./data/error/")
```

### 3. 常见问题与最优处理方案 (Challenges & Solutions)

这是您最关心的部分，针对**硬件上传到云端**这一具体环节的挑战分析。

#### 🔴 问题一：网络不稳定导致的数据丢失或损坏
*   **场景**：门店 WiFi 信号差，上传传了一半断了；或者上传成功但文件只有一半（截断）。
*   **最优处理方案**：
    1.  **本地持久化队列 (Local Queue)**：**绝对不要**把待传数据只放在内存里。必须落盘（存 SD 卡）。即使树莓派突然断电，重启后也能继续传。
    2.  **MD5 校验 (Checksum)**：硬件端计算 MD5 传给云端，云端收到后重新计算比对。不一致则要求重传。
    3.  **应用层重试 (Application Retry)**：不要依赖 TCP 的重传。代码层面必须捕获 `ConnectionError` 并进行循环重试。

#### 🔴 问题二：算力洪峰 (Thundering Herd) - 定时上传模式特有
*   **场景**：设定所有设备凌晨 02:00 上传。02:00:01 秒，云端带宽被占满，V100 显存爆炸。
*   **最优处理方案**：
    1.  **随机抖动 (Jitter)**：设备端不要写死 `02:00`。而是 `sleep(random(0, 3600))`。让 100 台设备分散在 1 小时内上传。
    2.  **云端限流 (Rate Limiting)**：Service A (API 网关) 设置最大并发数为 50。第 51 个请求直接返回 `429 Too Many Requests`。
    3.  **设备端退避 (Backoff)**：设备收到 429 错误后，不要立即重试，而是等待 `2^n` 秒（指数退避），给服务器喘息时间。

#### 🔴 问题三：时钟不同步导致的数据错乱
*   **场景**：树莓派断电后时间重置为 1970 年。上传的音频时间戳全是错的，无法与 P4 的视觉数据对齐。
*   **最优处理方案**：
    1.  **强制 NTP 检查**：`smart_recorder.py` 启动时，必须先 ping 通 NTP 服务器并校准时间。**如果时间未校准，禁止开始录音**（宁可不录，也不录错误时间的数据）。
    2.  **硬件 RTC (可选)**：如果现场完全无网，给树莓派加一个 DS3231 实时时钟模块（几块钱），断电也能走时。

#### 🔴 问题四：小文件碎片化 (Small File Fragmentation)
*   **场景**：VAD 切分太碎，产生了大量 1-2 秒的音频文件。频繁建立 HTTP 连接导致握手耗时比传输耗时还长。
*   **最优处理方案**：
    1.  **边缘合并 (Edge Merge)**：上传线程在扫描 `pending/` 目录时，如果发现有连续的 10 个小文件，使用 `ffmpeg` 或简单的二进制拼接，将它们合并成一个 30秒~1分钟 的包再上传。
    2.  **HTTP Keep-Alive**：在 Python `requests` 中使用 `Session` 对象，复用 TCP 连接。

---

### ✅ 总结：您的执行动作

1.  **修改树莓派代码**：不要直接上传。实现 `pending/` 文件夹监控逻辑，确保断网后文件能积压在本地，联网后自动补传。
2.  **修改云端 Service A**：增加 MD5 校验逻辑；增加 Redis 队列缓冲（不要收到文件就立马处理，先存盘、入队、返回成功）。
3.  **配置 NTP**：确保每一台树莓派的时间是精准的。

## ☁️ 第三部分：云端微服务架构 (Cloud Architecture)

为了应对高并发和多模态分析，云端（V100服务器）采用 **微服务拆分架构**。

### 3.1 服务 A：智能听觉网关 (Project 1 - The Ear)
*   **定位**：高并发 I/O 守门员。
*   **技术栈**：FastAPI + Redis。
*   **接口**：
    *   `POST /upload`: 接收音频文件 -> **不处理，直接存入 Redis 队列** -> 返回 200 OK。
    *   `POST /heartbeat`: 接收设备心跳 -> 更新设备状态表。
*   **后台 Worker**：
    *   从 Redis 队列取任务。
    *   运行 **V3.3 引擎** (ASR + 声纹 + 边界校正)。
    *   结果写入 **IoTDB** (时序对齐)。

### 3.2 服务 B：通用 LLM 服务 (Project 2 - The Brain)
*   **定位**：纯推理计算单元。
*   **技术栈**：vLLM + Qwen2.5-7B-Int4。
*   **配置**：显存占用限制 50% (与服务 A 共存)。
*   **接口**：`POST /v1/chat/completions`。

### 3.3 服务 C：业务编排中心 (Project 3 - The Hand)
*   **定位**：业务逻辑与多模态融合。
*   **技术栈**：Python 脚本 (无显卡依赖)。
*   **逻辑**：
    1.  **监听**：轮询 IoTDB 或 Redis 消息，发现新对话数据。
    2.  **融合**：根据时间戳，从 P4 服务器拉取视觉标签。
    3.  **分析**：组装 Prompt (含情感分析要求) -> 调用服务 B。
    4.  **决策**：解析 JSON 结果 -> 触发报警或生成报表。

## 🛡️ 第四部分：挑战场景与应对策略

针对三种不同业务模式的最优处理方案。

### 场景一：通用挑战 (基础物理层)
| 挑战 | 解决方案 |
| :--- | :--- |
| **环境噪音** | **双重降噪**：硬件端开启 ReSpeaker DSP 增益；云端 V3.3 引擎启用 AS-Norm 抗噪。 |
| **时钟漂移** | **NTP 强制同步**：树莓派启动脚本中加入 `ntpdate pool.ntp.org`，确保文件名时间戳精准。 |

### 场景二：实时上传模式 (安防/监控)
| 挑战 | 解决方案 |
| :--- | :--- |
| **网络抖动** | **本地缓冲队列**：上传线程与录音线程解耦。网络断开时，录音继续写入 SD 卡队列；网络恢复后自动追赶上传。 |
| **云端并发** | **Redis 削峰**：API 层只收不处理。Worker 层单线程匀速消费，保护 V100 显存不溢出。 |

### 场景三：定时/批量上传模式 (客流/绩效)
| 挑战 | 解决方案 |
| :--- | :--- |
| **算力洪峰** | **错峰上传 (Jitter)**：每台设备随机生成上传时间窗口（如 02:00-04:00 之间随机），避免同时撞击服务器。 |
| **数据丢失** | **心跳监控**：即使不传音频，设备也必须每 5 分钟发一次心跳。云端若 15 分钟未收到心跳，立即短信报警“设备离线”。 |
| **时空错位** | **元数据解析**：云端严禁使用 `System.now()`。必须解析文件名中的 `{timestamp}` 作为 IoTDB 的写入时间，以保证与白天发生的视觉数据对齐。 |
